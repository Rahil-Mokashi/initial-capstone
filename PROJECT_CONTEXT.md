# Petrol Pump ERP - Project Context

## Project Objective
Build a complete Petrol Pump Management ERP capable of managing all petrol pump operations including fuel inventory, sales, procurement, HR, reporting, and more. The application is designed to be deployed on a petrol pump desktop computer and must operate reliably even when there is NO INTERNET CONNECTION.

## Business Understanding
A petrol pump management system needs to handle fuel inventory, sales, procurement, supplier management, employee management, shift management, fuel reconciliation, customer credit, and reporting. The system is a desktop-only application with SQLite database, capable of operating entirely offline.

## Current Architecture
- **Frontend**: PySide6 (Qt for Python)
- **Database**: SQLite (single file, zero-config)
- **ORM**: SQLAlchemy 2.x
- **Reports**: ReportLab for PDF, openpyxl for Excel
- **Packaging**: PyInstaller for desktop executable, offline deployment
- **Reporting**: ReportLab for reports
- **Packaging**: PyInstaller

## Database Design
- Single SQLite file (petrol_pump.db)
- UUID primary keys planned
- Foreign key constraints — actually enforced at the DB level via `PRAGMA foreign_keys=ON` on every connection (app/database/connection.py), not just declared in the ORM; see Known Bugs (Fixed)
- WAL mode enabled via `PRAGMA journal_mode=WAL` on every connection (same location)
- Proper normalization

## Build audit remediation (2026-08-17, user-requested)
The user asked for a full evaluation of every aspect of the app, then for every finding to be fixed. ### Block 1-2: the blockers and data integrity

- [x] **Multi-step financial operations are now atomic** (audit finding #02, the top data-integrity item). CLAUDE.md requires "Always use transactions for financial operations" and "Never allow partial financial writes", but every repository committed independently via `safe_commit`, so a service method spanning several tables was really several transactions. `create_sale` was four or five: the Sale row, the tank ISSUE transaction plus the tank's stock decrement, the Sale's update with the transaction id, and the Payment row. A constraint violation, a disk-full or a crash between any two left fuel gone from a tank with no sale accounting for it, or a completed sale with no payment record silently corrupting shift reconciliation.
  - `unit_of_work(session)` (`app/repositories/base.py`) is one transaction per business operation, committed on clean exit and rolled back on any exception. It nests, so a service calling another service (SaleService -> TankService -> CreditService) joins the outer transaction rather than committing early — only the outermost block commits.
  - `safe_commit()` now **flushes** instead of committing when a unit of work is active. Flushing emits the statements inside the caller's transaction, so generated defaults are populated and the repositories' follow-up `session.refresh()` still works. This is what let all 82 existing `safe_commit` call sites stay unchanged and still become atomic as a group — a deliberately minimal-blast-radius design, since the alternative was editing 28 repository files.
  - Wrapped: `SaleService.create_sale`/`cancel_sale`, `TankService`'s stock movements and fuel reconciliation, `ProcurementService.create_purchase_order`/`record_payment`/`record_post_dip_and_unload` (the widest write in the app — dip reading, tank receipt, tank stock, delivery record, recomputed PO status), `ReconciliationService.perform_shift_reconciliation`, `CreditService.record_customer_payment`.
  - `tests/test_transaction_atomicity.py` was written **before** the fix and failed against the old code: it forces a failure at the payment step of `create_sale` and asserts no Sale, no Payment, no tank transaction and no stock change survive. Also covers the successful path (so the fix cannot over-correct into never committing) and the nesting guarantee.

- [x] **Fuel selling prices exist** (audit finding #01, the single largest functional gap). `seed.py` created Petrol/Diesel/Power at `rate_per_liter=0.00` and **nothing in the app could change that** — the only write to that column anywhere in the codebase was that one seed line. On a fresh install every sale computed `quantity x 0.00 = 0.00`, and sales, payments, credit balances, reconciliation, dashboard KPIs and Business Insights all reported zero. The demo seeder hid it by writing prices directly.
  - `FuelService` (`app/services/fuel_service.py`), `FuelPriceHistory` model (migration `53548fd46c68`), `app/schemas/fuel.py`, `app/repositories/fuel_price_history_repository.py`, `app/ui/fuel_price_window.py`, "Fuel Prices" dashboard card.
  - New `Permission.FUEL_PRICE_VIEW`/`FUEL_PRICE_MANAGE`. Changing a price is deliberately a **stricter** grant than `INVENTORY_MANAGE` because it silently changes the revenue of every future sale — the same reasoning that gave `SHIFT_REOPEN` and `EXPENSE_APPROVE` their own permissions. Manager gets both; Accountant/Shift Supervisor/Attendant get view only (an attendant quotes the price to the customer).
  - **Price history closes audit finding #07 at the same time**: `Fuel.rate_per_liter` answers "what is the price now", which is all a new sale needs since `Sale` snapshots its own rate; `FuelPriceHistory` answers "what was it on the 14th and who changed it", which is what an audit and any margin analysis need. Retrofitting history is much harder than starting with it, hence building both together. The seeded 0.00 placeholder is recorded as *no predecessor* rather than as a price someone set.
  - `SaleService` now refuses to sell an unpriced fuel rather than booking a 0.00 sale. The guard (`FuelService.ensure_fuel_is_priced`) is a plain static helper with no `@require_permission` of its own — re-checking a *different* permission mid-operation is exactly the layering bug the `TankService.*_as_related_action` split was created to fix.

- [x] **Document-number sequences no longer break after a restore** (audit finding #03). `next_receipt_number`/`next_employee_code` derived from `COUNT(*) + 1`. A count is not a high-water mark: the two diverge the moment any row disappears, and `COUNT(*) + 1` then returns a number that already exists — which the `unique=True` index rejects, blocking every further sale with an error an attendant cannot resolve. Not hypothetical, because the app ships a **restore** feature: restoring to an earlier backup rewinds the count while the receipt numbers already printed on customers' receipts stay issued. Both now derive from `MAX()`, which rewinds with the data, with a fallback so a malformed legacy value cannot wedge sales entirely.

- [x] **Money rounding has a declared policy** (audit finding #08). `amount = quantity * rate` was left at whatever precision the multiplication produced (a 3 dp quantity times a 2 dp rate gives 5 dp) and rounded implicitly by the `Numeric(10, 2)` column under Python's default `ROUND_HALF_EVEN` (banker's rounding). Indian invoicing convention is `ROUND_HALF_UP`, so exact halves went the wrong way — by a paisa, only sometimes, which is precisely the kind of variance nobody can explain when a month of reconciliation totals disagree. `app/core/money.py` owns that decision in one place (`money()` for 2 dp paise, `volume()` for 3 dp litres, both half-up, both converting floats via `str` so binary floating-point error never enters). `tests/test_money_and_sequences.py` pins both this and the sequence behaviour.

- [x] `.gitignore` gained `*.db-shm`/`*.db-wal` (audit finding #42) — WAL mode always creates those sidecar files, so they were permanently untracked-but-present in `git status`.


- [x] **Every datetime read from the database is timezone-aware UTC** (audit finding #04, the last blocker). SQLite has no native datetime type, so SQLAlchemy stores a `DateTime` as an ISO-8601 string and the tzinfo label is lost on the round trip. The instant written was correct UTC; what was missing was the statement that it *was* UTC. So comparisons against the aware `datetime.now(timezone.utc)` the app correctly uses either raised `TypeError` or — when both sides happened to be naive — silently compared a local wall-clock reading against a UTC one. That is exactly the already-shipped fuel-reconciliation bug, fixed at two call sites and worked around at a third (`_as_aware_utc`), while the trap stayed armed everywhere else because it lived in the *column type*.
  - `app/database/types.py`'s `UtcDateTime` (a `TypeDecorator`) normalises on bind and re-attaches `timezone.utc` on result, applied to every `DateTime` column across 21 model files.
  - **No data migration was needed, and that is why this approach was chosen** over `DateTime(timezone=True)` + a batch migration: checking what SQLite actually stores first showed the bytes on disk were already correct UTC instants, so the type keeps the on-disk format byte-identical and only supplies the label on read. Every database already in the field keeps working untouched, and a test asserts the format is unchanged so a future regression fails loudly.
  - `local_day_bounds_utc` no longer strips tzinfo — that stripping was itself a workaround for the naive columns (its own docstring said so) and keeping it would have reintroduced the mismatch in the other direction.
  - Turning the columns aware surfaced 9 previously-passing tests that had been silently comparing UTC against local time.

- [x] **Value invariants are enforced by the database** (audit finding #05). 15 `CHECK` constraints across 9 tables (migration `fa88f5c33f4c`). The project already enforced foreign keys at the DB level rather than trusting the ORM; leaving every value rule Python-only was a strange asymmetry given the `.db` file is directly reachable with any DB browser on the forecourt PC. Two things went wrong and are worth recording:
  - The migration failed with `FOREIGN KEY constraint failed` on `DROP TABLE fuels`. SQLite cannot `ALTER TABLE` to add a constraint, so Alembic batch mode *rebuilds* the table — and dropping the original is refused while other tables reference it. `alembic/env.py` now suspends FK enforcement for the migration (issued on the raw DBAPI connection, since `PRAGMA foreign_keys` is a no-op inside a transaction) and runs `PRAGMA foreign_key_check` afterwards, raising if anything was orphaned.
  - `ck_tank_transactions_quantity_positive` was **wrong** and broke 53 tests. `TankTransaction.quantity` is a *signed stock delta* by design (ISSUE negative, RECEIPT positive, ADJUSTMENT either), so a positivity constraint contradicts the domain model. Now `quantity != 0`. It slipped past a pre-flight check against the demo database because `scripts/seed_demo_data.py` inserts bulk history directly rather than through the service layer, so that data never exercised the real code path — validating a constraint against data that did not come through the code it constrains proves nothing.

- [x] **Dev tooling exists** (audit findings #20, #21). `pyproject.toml` (PEP 517/518/621) now gives ruff, mypy, pytest and coverage somewhere to be configured — previously there was nowhere, which is why ~26,000 lines had no linting. Ruff enables `DTZ` (naive-datetime) checks deliberately, given this project's history with that bug class. mypy is non-strict and scoped to services/repositories/core first. 33 unused imports auto-fixed; the ~500 remaining findings are cosmetic modernisation left for a separate pass rather than burying real changes in churn.

- [x] **`pytest-qt` substantially mitigates the test-suite crash** (audit finding #25, partially). Three UI modules that previously either aborted the interpreter or took over an hour now run together in 19 seconds. The *full* suite still crashes around 22% — it is cumulative resource exhaustion, not any single module (verified: `test_core_setup.py` passes alone and after a Qt module) — so CI's batching stays for now. Ceiling raised from ~3 modules to ~10, not removed.

- [x] **Real bug found by the new linter**: `CreditService.is_overdue` computed the due date from `oldest_sale.sale_at.date()`. Now that datetimes are aware UTC, `.date()` yields the *UTC* calendar date, not the local business date — so on IST a credit sale at 02:00 local is dated to the previous day and the customer is marked overdue a day early. `app/core/dates.py` gained `local_date_of()` (the inverse of `local_day_bounds_utc`).


### Block 4: responsiveness (started)

- [x] **Slow work runs off the GUI thread** (audit finding #15, problemstatement.md #44 — "Do heavy operations outside the main UI thread. Never freeze the application while generating a large report."). The app previously had no threading at all. `app/ui/background.py`'s `run_in_background()` wraps `QThreadPool`/`QRunnable`; results return via a Qt signal, which Qt delivers as a *queued* connection across threads, so callbacks land on the GUI thread where touching widgets is legal — thread-safety by construction, no locks in calling code. Wired into the Backups screen first (backup now, integrity check) because those take plain data in and return a file path, touching no ORM objects.
  - **Note for extending this to report queries**: a SQLAlchemy `Session` is not thread-safe. A database worker needs its own Session and must return plain data, never live ORM instances — those would lazy-load from the wrong thread's session the moment the GUI touched them.
  - Writing the tests found a real bug in the helper: closing a window while a task runs left the callback re-enabling a button whose C++ object had already been destroyed with its parent (`Internal C++ object already deleted`). Qt owns widget lifetime through the parent tree independently of Python reference counting, so a Python proxy outliving its C++ object is normal rather than exceptional. Guarded with `shiboken6.isValid()`.

- Recorded for a later pass: `mypy app/services/` reports ~79 errors, nearly all `Column[str]` vs `str`. These are artifacts of the SQLAlchemy 1.x-style `Column()` declarations rather than 2.0's `Mapped[str]` annotations, not real defects. Fixing them properly means migrating all 31 models to `Mapped[]`, which is its own focused change. Ruff's ~500 remaining findings are likewise cosmetic modernisation (`Optional[X]` -> `X | None`, `List` -> `list`) deliberately left out so they do not bury real changes in churn.


### Edge-case / rule-interaction hunt (2026-08-17)

`tests/test_edge_cases.py` (22 tests) was written specifically to hunt for logic errors rather than to cover features. Every other suite tests one service doing the thing it is for; this one probes the *seams* — exact boundaries, repeated actions, and whether a reversal in one module propagates to another — because that is where logic errors actually live. The individual rules are usually right; the bugs are in how two right rules combine.

- [x] **Third local-vs-UTC date bug found and fixed**: `CreditService.get_customer_statement` dated each line with `sale.sale_at.date()`, which now yields the *UTC* calendar date, so on IST a credit sale made at 02:00 local (20:30 UTC the previous day) was dated a day early **on a customer-facing statement**. Fixed with `local_date_of()`. A follow-up sweep confirmed no remaining `.date()` calls on stored datetimes anywhere in `app/`.
  - Worth noting the pattern: this bug class has now appeared three times (fuel reconciliation day boundaries, `is_overdue`, and this). Whenever a `.date()` is added to a stored datetime, grep for the others.
  - Checked and *not* a bug: `should_take_scheduled_backup` compares `datetime.fromtimestamp(st_mtime)` against `datetime.now()`, both naive local, so it is internally consistent. Fragile if either side ever becomes aware, but correct today.

- Verified correct (no changes needed): cancelling a credit sale frees the credit back up and the freed credit is genuinely reusable; cancelling returns the fuel to the tank; a sale cannot be cancelled twice; a cancelled sale's payment cannot then also be refunded (double reversal); a refunded payment cannot be refunded again; a sale landing exactly on the credit limit is allowed while one paisa over is refused; a sale draining a tank exactly to zero is allowed while 0.001 more is refused and leaves no row behind; a cancelled sale is excluded from shift reconciliation (otherwise every reconciliation after a cancellation would show a false shortage and blame an attendant for it); a shift cannot be reconciled twice; zero/negative quantities, credit sales with no customer or no credit account, blank cancellation reasons and inactive nozzles are all rejected; and 100 sales of 0.333 litres sum exactly with no floating-point drift.


- [x] **Pagination, repository and service layer** (audit finding #16, first half). `SaleRepository`/`PaymentRepository` `list_all()` now take `limit`/`offset`, with `limit` defaulting to `None` so every existing caller — including all the reporting code, which genuinely needs every row — is unchanged. Paging is deliberately **opt-in**, which is what made this safe to land without auditing every call site. `count_all()` gives a pager its total via `SELECT COUNT(*)` rather than `len(list_all())`. Both order by their own timestamp descending (`Sale.sale_at`, `Payment.payment_at` — note `Payment` does not inherit `EntityMixin` so it has no `created_at`), and that same column is the page boundary so pages cannot interleave.
  - **Still outstanding for this finding**: the UI still calls `list_sales()` with no limit, so the benefit is not yet realised on screen. That needs a pager control and pairs naturally with moving from `QTableWidget` to `QTableView` + `QAbstractTableModel`, which fetches only the visible rows. Do the two together rather than twice.
  - The test worth keeping is `test_paging_returns_every_row_exactly_once`: the failure mode worth guarding is not slowness but a page boundary that drops or repeats a row, which on a sales list means a transaction the operator cannot find, or one they count twice.


### Block 6: hardening (2026-08-17)

Prompted by the user asking what generic "how to ship an app" advice (rate limiting, Clerk/Firebase auth, row-level security, Redis, async jobs, load testing) means for this project. The honest answer is that most of it is written for **web SaaS** and does not transfer: there is no HTTP endpoint to rate-limit, cloud auth providers are architecturally impossible for an offline app, RLS is a Postgres feature (this app's equivalent is `@require_permission` in the service layer), and Redis would add a server to a deliberately server-free product. What *does* transfer are the principles, in translated form — and those became this block.

- [x] **Automatic lockouts expire** (audit finding #13) — the desktop equivalent of a login rate limit. `User.locked_at` (migration `d4475c941f23`) plus `LOCKOUT_DURATION_MINUTES = 15`. The old behaviour was a **permanent** lock until an admin cleared it, which on a night shift with no admin present turned a security control into an availability outage — and the predictable staff response to that is to share one never-locked login, which is worse than the attack it defended against. A control people route around is not a control. An administrator-applied lock (no `locked_at`) still never expires. The expiry is audit-logged.

- [x] **Audit trail is tamper-resistant AND tamper-evident** (audit finding #11, migration `52bf0b01839b`). Being precise about the distinction matters: truly *preventing* modification needs append-only storage the operator does not control, which an offline desktop app does not have. What is achievable is making modification *detectable*.
  - **Resistant**: `BEFORE UPDATE`/`BEFORE DELETE` triggers on `audit_logs` `RAISE(ABORT)`, so even direct SQL against the file fails.
  - **Evident**: each row stores SHA-256 over its own fields plus the previous row's hash, so every entry commits to the whole history before it. Altering or removing a row breaks the chain from there on. Same construction as a blockchain minus the distributed consensus, which would do nothing useful on one machine.
  - Both are needed — triggers can be dropped by anyone who can also run DDL, and the chain detects it when they do. The tests prove the layering by dropping the trigger *first* and then tampering.
  - `AuditService.verify_trail()` + a "Verify Trail" button on the Audit Log screen, running off the GUI thread. Verification is itself audit-logged, including when it fails.
  - **Bug found while testing**: `AuditLog.id`/`created_at` come from Python-side column defaults SQLAlchemy applies at INSERT time, not at construction — so hashing before the insert covered an `id` of `None`, and verification failed on untampered data. Both are now materialised before hashing.
  - Rows predating the chain have NULL hashes and are treated as unverifiable rather than as tampering, so existing installations do not false-alarm.

- [x] **Backups can be copied off the machine they protect** (audit finding #38). `copy_backup_to()` + `latest_offsite_copy_age_days()` + `BackupService.copy_backup_offsite()`. The copy is integrity-checked on arrival, because a failing USB stick can accept a write and hand back a corrupt file — reporting success there would leave the operator believing they were protected. Built to **nag** rather than schedule: a pump has no IT staff and the machine is not guaranteed to be running at any given time. An off-device copy is also audit-logged as a security event, since it is every financial record in the business leaving the machine.
  - Still outstanding: a "Copy to..." button and staleness banner on the Backups screen. The service layer is ready for both.


### Settings screen and company profile (audit finding #33, 2026-08-17)

The highest-value remaining item, despite looking like plumbing: every receipt, statement and report the app printed carried **no business identity** — no pump name, no address, no GST number. A receipt with none of those on it is a slip of paper, not a receipt, and it cannot be handed to a customer.

- [x] `AppSetting` (migration `d6e5393626bf`) is a **single-row table, not a key/value store**. Both shapes are defensible and the choice is worth stating: typed columns let the *schema* enforce what exists, and nothing lets two callers disagree about whether the key is `gst_number` or `gstin` — the same reasoning that put value invariants in CHECK constraints rather than only in Python. Created on first read, so an existing installation upgrading into this feature needs no data-migration step.

- [x] `SettingsService.get_company_profile()` is **deliberately undecorated** — reading the letterhead is a side effect of printing, which the actor is already authorised for, not a separate "view settings" action. Re-checking a different permission there is exactly the layering bug that `TankService`'s `*_as_related_action` split exists to avoid, and it is the third time that pattern has applied.
- [x] Changes are audit-logged with old → new values, since the profile appears on every document the business issues. Saving with nothing changed writes nothing, so opening Settings and clicking Save does not fill the trail with entries recording that nothing happened.

- [x] Also unblocks the previously-deferred configurable backup location (`offsite_backup_dir`), and gives print configuration somewhere to live next.

- The email validator accepted `@x.com` — splitting on `@` and checking only the domain half ignores whether anything precedes it.

### Notifications / local application alerts (problemstatement.md #43, 2026-08-17)

Thirteen alert types were specified: low fuel, fuel variance, cash shortage, cash excess, payment mismatch, failed reconciliation, attendance issue, unauthorized action, pending approval, outstanding credit, supplier payment due, backup failure, database error. All thirteen are implemented.

- [x] **No `notifications` table was created, and that is the central decision.** The requirements list `notifications` among the database tables, but ten of the thirteen alert types describe a *condition*, not an event — "low fuel" is true exactly as long as the tank is low. A stored row records that the condition was true once, and keeping it honest afterwards needs a second mechanism to expire it when the tank is refilled, the expense is approved, the customer pays. The failure mode of that mechanism is an alert screen confidently reporting problems that were fixed weeks ago, and nobody trusts that screen twice. This project already refuses the same trade for `SupplierInvoice.status`, `PurchaseOrder.status` and `CreditService.get_outstanding_balance`, all recomputed rather than accumulated precisely so they "can never silently drift". `NotificationService` (`app/services/notification_service.py`) derives every condition alert from live data on each refresh, so an alert cannot be stale — there is nothing to go stale.
- [x] The three genuine *event* alerts (unauthorized action, database error, audit-chain break) are read from `AuditLog`, which is already append-only and hash-chained — the right home for them, and again no new table. They age out after `NOTIFICATION_RECENT_EVENT_DAYS` (7) since, unlike conditions, they cannot clear themselves.
- [x] **Backup failure is derived from the absence of a recent backup file**, not from a recorded failure event (`NOTIFICATION_BACKUP_OVERDUE_HOURS` = 48, twice the automatic interval). That is the stronger test: it does not care *why* there is no backup — full disk, revoked permission, a crash before the write, or a code path nobody added logging to all produce the same observable fact, that the thing needed in an emergency is not there.
- [x] **There is no "mark as read".** Dismissing an alert whose condition is still true is a way to hide a real problem. The way to clear an alert is to fix what caused it; volume is handled by severity ordering and a per-category cap (`NOTIFICATION_MAX_PER_CATEGORY` = 5) with an honest "N more" line that never hides the count.
- [x] **A real security gap closed on the way**: `require_permission` raised `PermissionDeniedError` and kept no record at all. A denial is the one security event most worth keeping, because a single one is a mis-click while a burst from one account is somebody probing what they can reach — and only the trail distinguishes them. `AuthService.record_permission_denied` now records it (audit-write failures are swallowed so they cannot mask the permission error itself), the decorator calls it at the single chokepoint every check already passes through, and the alert escalates from WARNING to CRITICAL on repetition rather than on any single event.
- [x] `BackupService.check_integrity` and `AuditService.verify_trail` now record **distinct event types** for pass and fail (`database_integrity_failed`, `audit_trail_tampered`) instead of one event whose description happens to read "ok"/"intact" — otherwise finding past failures means pattern-matching a human-readable string, which stops working the first time the wording changes.
- [x] Per-category permission gating, reusing `DashboardService.get_summary`'s pattern. The two approval categories are gated on the *approve* permission rather than the view one, since an alert saying "waiting for you" should only reach somebody who can act on it (a Shift Supervisor performs reconciliations but cannot approve them).
- [x] One failing producer cannot blank the screen — each is isolated, because an alert list is consulted precisely when something is already wrong, which is when a query is most likely to throw. Losing one category beats showing an empty, falsely reassuring screen. The UI says so explicitly rather than rendering "all clear" on failure.
- [x] `app/ui/notification_window.py` + a self-colouring count in the dashboard top bar; new `alertCard`/`alertsButton` styles extend the existing palette (danger red / accent amber / primary indigo) with no new colours.
- [x] 31 service tests (`tests/test_notification_service.py`) + 11 UI tests (`tests/test_notification_ui.py`). The property tested hardest is that an alert *disappears* once its condition is fixed — that is the whole justification for deriving rather than storing, so leaving it untested would leave the design decision unprotected.

**Performance/crash lesson recorded** (three attempts, worth not repeating): computing the alert list inside `MainWindow.__init__` crashed the interpreter — a garbage collection landing inside SQLAlchemy's result processing while a freshly-built Qt widget tree was still settling. Deferring it with `QTimer.singleShot(0, ...)` only moved the crash. Reducing it to a *single trivial query* crashed too, which is what proved the problem is not the amount of work but the moment: **database work does not belong near Qt widget construction or teardown in this application.** The badge is therefore filled in from the session tick that already runs every 60s against a settled, idle window, and refreshed when the Alerts screen opens. Separately, `get_notifications` memoises permission lookups for the duration of one call — `check_permission` walks user → role → permissions through the ORM, and a single refresh was issuing a dozen identical lazy-loaded queries.

### Test-suite: both defects fixed, suite runs in one process (audit finding #25, 2026-08-17)

**676/676 in a single `pytest tests/` invocation, ~4m10s.** CI's four alphabetical batches are gone.

**Confirmed over five consecutive full-suite runs** (248s, 295s, 300s, 242s, 261s — all 676 passed, exit 0, no crash frames and no `faulthandler` stack dumps). Five runs rather than one is deliberate: an earlier attempt at this fix was declared done on a single green run and the very next run stalled. Worth noting that the fifth ran *concurrently with a PyInstaller build*, since that kind of contention previously produced apparent hangs — passing under it is a stronger signal than another idle-machine green tick. What made this take so long is that **two unrelated defects were tangled together**, and every attempt to explain both with one cause failed. Separating them is the real result.

**Defect 1 — a native crash (Windows access violation).** Caused by a widget leak: 17 of the 20 UI test modules never use pytest-qt's `qtbot`. Each builds its own `QApplication` and constructs real windows inside test functions with nothing registered for cleanup. Qt owns widget lifetime through the parent tree *independently of Python reference counting*, so a window whose last Python reference is dropped is not freed — it survives with its timers, its children and (on the dashboard) one `QGraphicsDropShadowEffect` per card. These accumulated all session until an allocation tipped the process over, which is why the crash appeared to move between files and to be caused by whichever change came last. Fixed by an autouse fixture in `tests/conftest.py` that closes, unparents and deletes leftover top-level widgets after each test, then calls `processEvents()` — without that call `deleteLater` only queues the deletions and they pile up exactly as before.

**Defect 2 — an intermittent hang with no fault at all**, the process sitting with flat CPU. Found by setting `faulthandler_timeout = 100` in `pyproject.toml`, which dumped the stack of the stuck test:

```
app/ui/shift_window.py, line 316 in _close_shift
tests/test_shift_ui.py, line 223 in test_detail_dialog_assign_nozzle_and_close_shift
```

The test stubbed `QMessageBox.question` but **not** `QMessageBox.warning`, then deliberately drove the rejected-close path — which reports the refusal through `warning()`, a modal dialog calling `exec()` and waiting for a click no test can make. It hung only when no queued event happened to dismiss the dialog, which is why it passed most runs. It also explains the wild timing variance seen earlier (301s to 601s per full-suite run) and why `test_shift_ui.py` alone dropped from ~24s to ~4s once fixed.

- [x] The test now stubs `warning` too, and asserts the refusal was actually *surfaced* rather than only that the shift stayed open — otherwise a change that silently swallowed the error would still pass while leaving the operator with no idea why the shift did not close.
- [x] `tests/conftest.py` gained a guard so this class of bug cannot silently return: every `QMessageBox` static helper gets a non-blocking default. The defaults are chosen so a leaked dialog cannot quietly approve anything — acknowledgements return `Ok`, confirmations return **`No`**, so an unstubbed destructive action is declined rather than performed. A test needing a different answer stubs it locally and overrides the guard.
- [x] `QInputDialog` is deliberately **not** guarded: its helpers return values the calling code then acts on (a reason string, a meter reading), so a blanket default would silently change what a test exercises instead of merely unblocking it.
- [x] `faulthandler_timeout = 100` is kept permanently, so any future stall self-diagnoses instead of producing a silent hang with nothing to work from.

**Two process lessons worth keeping.** First, this was declared fixed after one green run and the very next confirmation run stalled — in nondeterministic territory a single green run is not evidence. Second, the fact that *every individual test always passed* while only the process ever failed was the strongest available clue that the fault was in harness and resource handling rather than in application code, and it went unread for too long.

**The actual root cause was a widget leak, not garbage collection.** 17 of the 20 UI test modules never use pytest-qt's `qtbot`: each builds its own `QApplication` in a module-scoped fixture and then constructs real windows inside test functions with nothing registered for cleanup. Qt owns widget lifetime through the parent tree *independently of Python reference counting*, so a window whose last Python reference is dropped is not freed — it survives, along with its timers, its children, and (on the dashboard) one `QGraphicsDropShadowEffect` per card. Those accumulated for the entire session until some allocation tipped the process over. That is why the crash looked random, moved between files, and appeared to be caused by whichever change was made most recently.

- [x] `tests/conftest.py` gained an autouse fixture that closes, unparents and deletes every leftover top-level widget after each test, then calls `processEvents()` — without that call `deleteLater` only queues the deletions and they pile up exactly as before.
- [x] Fixed in **one** place rather than by retrofitting `qtbot.addWidget` across 17 files: one reviewable change, and it covers every UI test written in future instead of depending on the next author remembering.
- [x] Measured, not assumed. `tests/test_shift_ui.py` stalled indefinitely on 3 of 3 solo runs before the fix and passed 6 of 6 after it; the full suite went from aborting partway through to 676/676.
- The earlier `gc.freeze()` mitigation is kept — it reduces collector pressure over the large permanently-live population of module objects and Qt type wrappers, and is cheap — but it was treating a symptom. It cleared two of four batches and could never have fixed the underlying leak.

### Earlier (superseded) diagnosis, kept as a record of the wrong turn

The long-standing crash that forces `.github/workflows/tests.yml` to run the suite in four batches was diagnosed. ### Dependencies are pinned and locked (audit finding, Block 3 remainder — 2026-08-17)

`requirements.txt` carried only loose ranges (`SQLAlchemy>=2.0`), so two builds of the same commit could install different versions. For software that computes money and is handed to a client as a binary, that means a green CI run proves the code was sound *against whatever resolved that day*, and a rebuilt release tag could silently differ from the executable a pump is actually running.

- [x] `requirements.lock` (37 packages) and `requirements-build.lock` (+6 packaging tools) pin exact versions. `.github/workflows/tests.yml` and `release.yml` now install from them; `requirements.txt`/`pyproject.toml` keep the loose ranges and cross-reference the lock so the two cannot quietly drift.
- [x] **`pip freeze` is the wrong tool on this project and the lock header says why.** This machine uses the *global* Python installation, so freeze reports ~190 packages — jupyter, fastapi, twilio, scikit-learn — that the app never imports. Pinning those would misdescribe the project and drag unrelated upgrades into every build. The lock is instead the transitive closure of the declared dependencies, walked through installed package metadata with environment markers evaluated for this platform, then pinned at the installed version: **43 packages, not 190**.
- [x] Verified three ways rather than assumed: every third-party module imported anywhere under `app/` maps to a locked distribution (8 of 8 covered, none missing); `pip install --dry-run` resolves both lock files with no conflicts; and two entries that looked spurious (`librt`, `ast_serialize`) were checked and confirmed to be genuine dependencies of mypy 2.3.1 rather than closure-walk artifacts.
- [x] **Hash-pinned** (2026-08-18). Every requirement in both lock files carries the sha256 of each published distribution for that version, so pip verifies the artifact it downloaded is the one that was locked — defending against a tampered or substituted package on the index, not merely against a version drifting. pip enters `--require-hashes` mode automatically once any requirement has a hash, which is precisely why the lock had to be a complete dependency closure rather than only the direct dependencies. Multiple hashes are listed per requirement so the lock still installs on a different Python minor version or architecture. Digests are read from PyPI's published metadata rather than by downloading every wheel (PySide6 alone would make that half a gigabyte), and both files were verified to still resolve with `pip install --dry-run`.

## Architecture Decisions

### Encryption at rest: delegated to the OS, not implemented in the app (2026-08-17, audit finding #12)

The database is a single unencrypted SQLite file containing every sale, salary, customer balance and supplier price. SQLCipher (transparent page-level encryption) was considered and **deliberately not adopted**, because on an unattended desktop application the key has to come from somewhere and every option is worse than the alternative:

- **Embedded in the application** — anyone who can read the database can also read the executable, so it protects nothing while creating the *impression* of protection, which is worse than no encryption at all.
- **Typed at every startup** — a real improvement, but the pump cannot open in the morning if the one person who knows the passphrase is off sick, and it ends up on a sticky note beside the monitor within a week. The same "a control people route around is not a control" reasoning that drove the lockout-expiry fix (#13).
- **Held by the operating system** — genuinely correct, and exactly what full-disk encryption already provides.

So protection is delegated to BitLocker, where key management is already solved properly, rather than reimplemented badly inside the application. `docs/administrator-guide.md` now has a section telling the administrator specifically what to do: enable BitLocker on the data drive, use BitLocker To Go for USB backups (an off-device copy leaves the machine's disk encryption behind — and a lost USB stick is far likelier than a stolen PC), restrict the data directory by Windows account, and never cloud-sync the file.

The important part of this decision is that it is now **recorded rather than merely omitted**. An unencrypted database that nobody decided about is a defect; an unencrypted database with a documented threat model and an administrator procedure is an engineering trade-off. If the deployment context changes — a multi-tenant install, a laptop that leaves the site — revisit it here.

## UI/UX Decisions
- The client expects a clean, elegant, polished UI (not a bare functional stub) for every screen, balanced against the problem statement's UX priorities (speed, minimal clicks, large readable numbers for a busy pump environment). `app/ui/styles.py` holds one shared stylesheet so every future screen stays visually consistent — extend it rather than styling widgets ad hoc.
- Explicit direction (2026-08-15): make the UI "eye catching and minimal at the same time." Palette refreshed to one confident indigo primary (`#4F46E5`) with a single sparingly-used amber accent, rather than adding more colors. Applied concretely via: a split-panel login screen (gradient brand hero on the left with a badge/tagline/feature bullets, the form card on the right) instead of a bare centered form, and a real landing dashboard on `MainWindow` (personalized greeting, today's date, clickable icon-badge quick-access cards to Employees/Attendance/Shifts) instead of a static "Welcome" label. Both keep the same restrained, whitespace-driven language as the rest of the app — eye-catching comes from hierarchy and one strong color, not decoration.
- Known Qt/QSS gotcha worth remembering for future custom widgets: a plain `QWidget` subclass needs `self.setAttribute(Qt.WA_StyledBackground, True)` or its stylesheet `background-color`/`border`/`border-radius` will silently not render (see `DashboardCard` in `app/ui/main_window.py`). Built-in widgets like `QFrame`/`QPushButton`/`QDialog` don't need this.

## Auto-aggregate cash sales on nozzle assignment close (2026-09-02, user-requested)
The user pushed back hard on manual per-sale Terminal entry: a single desktop terminal can't realistically be the entry point for every individual cash transaction across a busy forecourt, and initially asked to remove sales tracking outright. Removing it was rejected as disproportionate — `Sale` is the load-bearing record for Payments, Credit, Reconciliation, most Reports, the Dashboard KPI strip, and the Analytics forecast, all built and tested across Phases 11-16. The actual bottleneck is specific to cash (anonymous, no need for a per-transaction ledger row) rather than credit/UPI/card (which genuinely need a customer link or a payment reference) — confirmed with the user via `AskUserQuestion` before implementing.
- [x] **`SaleService.settle_assignment_cash(actor_user_id, assignment)`** (`app/services/sale_service.py`): computes `dispensed = assignment.closing_meter - assignment.opening_meter` (the same meter-reading figure fuel reconciliation already trusts), subtracts every already-COMPLETED sale's quantity for that exact shift/nozzle/employee regardless of payment method (cash included — Terminal still allows manually ringing up an individual cash sale, e.g. for a customer who wants a receipt, and that volume must not be double-counted into the aggregate on top of itself), and posts the positive remainder as one lump `CASH` sale with no customer via a new `create_sale_as_related_action`. Returns `None` (creates nothing) when the remainder isn't positive, rather than fabricating a zero/negative sale — the `sales` table's own CHECK constraint would reject that anyway, and a non-positive remainder is a discrepancy to investigate, not paper over.
- [x] **`SaleService.create_sale_as_related_action`**: an unchecked twin of `create_sale`, mirroring `TankService.record_transaction_as_related_action`'s exact reasoning — it exists so `settle_assignment_cash` can create a sale on behalf of a caller (`ShiftService.complete_nozzle_assignment`, gated on `SHIFT_MANAGE`) whose own permission already authorizes this as a side effect, without also requiring that caller to separately hold `SALE_MANAGE`. `settle_assignment_cash` itself is deliberately undecorated too, matching `CreditService.ensure_credit_available`'s precedent exactly.
